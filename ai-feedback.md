# Обратная связь по архитектуре проекта (AI-feedback)

Учебный проект `serverest-api-tests` — набор API-тестов для тренировочного магазина ServeRest, а также упражнения по Java (дни 11–18). Ниже — разбор сильных сторон и зон роста с приоритетами.

## 1. Сильные стороны

- **Модульная структура по дням занятий** (`day11`–`day17`) — очевиден прогресс обучения, легко изолировать тему.
- **Актуальный стек**: Java 25, Gradle 9.6.1, JUnit 6, RestAssured 5.5.6 — современные версии, задел на будущее.
- **Особенность** — Cucumber c русскоязычными шагами и `# language: ru`, `Глоссарий`/`Предыстория` в `.feature` — наглядный пример BDD.
- **Чистое разделение** тестовых классов по типу: Junit-тесты, Cucumber-шаги/раннеры.
- После рефакторинга `ServeRestTest` использует `@DisplayName`, уникальные email, латиницу в данных — стало стабильнее и читаемее.

## 2. Зоны роста

### 2.1 Глобальная конфигурация RestAssured (статический mutable state)
`RestAssured.baseURI` задаётся в `@BeforeAll` каждого класса. Это глобальный статический ресурс — при параллельном запуске тестов или настройке разных баз для классов может происходить гонка состояний.

**Рекомендация**: вынести в общий `TestBase`, либо задавать URI через `given().baseUri(...)` в одном месте, либо читать из конфига/переменных окружения.

### 2.2 Зависимость порядка тестов от состояния
В `day17/ServeRestTest` тесты связаны через поля `userId`, `userEmail`, `token` и принудительный `@Order`. Это делает весь набор хрупким: падение RD-шага каскадно роняет все последующие.

**Рекомендация**: для каждого теста создавать собственные данные внутри теста или в `@BeforeEach`; ассерты не должны зависеть от результатов других тестов. `@Order` оставить только там, где без реальной зависимости не обойтись.

### 2.3 Не используется Jackson 2.19.2 (DTO-сериализация)
В `AGENTS.md` заявлен Jackson, но в API-тестах JSON передаётся текст-блоками `"""..."""`. Это дублирование, риск опечаток и потерю типизации.

**Рекомендация**: завести DTO (`Produto`, `Usuario`, `Login`) и сериализовать их через Jackson/`withObjectMapper`. Это упростит поддержку и откроет возможность переиспользовать одни и те же объекты в разных тестах.

### 2.4 Дублирование вспомогательного кода
`uniqueEmail`, `PASSWORD`, JSON-блоки повторяются между `ServeRestTest` и `ExtraServeRestTest`. Код-дупликация расползается.

**Рекомендация**: вынести общие helpers (построение email, авторизация админа, создание пользователя/товара) в переиспользуемый клиент-слой (например, `ApiClient`, `TestDataFactory`).

### 2.5 Система логирования
Используются `System.out.println` в нескольких местах (`BookingStepdefs`, старый код). Это не управляемая система логов.

**Рекомендация**: использовать SLF4J/логгер или сразу перейти на `@DisplayName` и собственные служебные сообщения внутри шагов; `println` заменить на `Logger`.

### 2.6 Cucumber-сценарий фактически не проверяет логику
Все шаги в `BookingStepdefs` делают только `println` со статусами, матчеров/ассертов реальной брони нет. Существующие `System.out.printf` не являются проверками.

**Рекомендация**: добавить бизнес-логику в объекты (например, `Restaurant`/`Table`) и реальные ассерты в шагах, чтобы сценарий что-то тестировал, а не печатал статусы.

### 2.7 Структура `.feature` и тегов
Одна фича на `booking.feature`, сценарии и структура сценария хорошо размечены тегами (`@smoke`, `@negative`, `@regression`), но шаги вызвали переполнение concern-файлов. При росте — разбивать на несколько `.feature`-файлов по функциональности (бронь, оплата, отмена).

### 2.8 Забытые/пустые файлы
`day18.java` существует как пустой класс `day18` и дублируется папкой `day18`. В папке `src/test/java/ru/alfabank/edu/day18` лежат скриншоты (`.png`), которые не должны находиться в исходниках. Парные `App.java`/`Main.java` в `day12` и `day13` смешивают учебный пример с тестовым проектом.

**Рекомендация**: удалить пустой класс, скриншоты перенести в документацию (например, `docs/`), а учебные `main`-примеры — отделить (отдельный модуль или папка `examples/`).

### 2.9 Cucumber-раннер фильтрует по тегу `@smoke`
`RunCucumberTest` включает `FILTER_TAGS_PROPERTY_NAME = "@smoke"` — это ограничивает запуск только smoke-сценариями.

**Рекомендация**: либо выносить выбор тегов в конфигруруемый параметр/профил Gradle, либо явно отделять smoke- и regression-раннеры.

### 2.10 Прочие моменты
- Дублирование зависимостей/возрастные версии: в `build.gradle` — это учебный проект, но `junit-platform-suite` и `cucumber-junit` различаются по версиям (1.10.2 / 7.33.0 / 7.34.4), стоит выровнять.
- Не раскрыт суффикс дилинга флагов (в `ExtraServeRestTest` используется `equalTo("Token...")` — сообщения API на португальском, стоит вынести в константы).
- При желании поднять надёжность: использовать `rest-assured` с `readTimeout`/`connectTimeout` и ретраями.

## 3. Приоритетные предложения (по стоимости/эффективности)

| Приоритет | Действие | Эффект |
|-----------|----------|--------|
| Высокий | Развязать зависимость тестов `day17` (данные на тест, `@BeforeEach`) | Устойчивость к падениям, параллельность |
| Высокий | Внедрить DTO + Jackson вместо JSON-блоков | Типизация, переиспользование, меньше ошибок |
| Средний | Вынести общий `ApiClient`/`TestDataFactory` | Устранение дублирования |
| Средний | Добавить реальные ассерты в Cucumber-шаги | Содержательные BDD-тесты |
| Средний | Заменить `println` на логгер/`@DisplayName` | Управляемые логи |
| Низкий | Убрать пустой `day18.java`, скриншоты в `docs/` | Чистота структуры |
| Низкий | Выровнять версии Cucumber/JUnit-платформы | Предсказуемый запуск |

## 4. Итог

Архитектура здравая и удобна для обучения: порядок по дням + комбинация JUnit/RestAssured и Cucumber покрывают оба формата API-тестирования. Ключевые улучшения, которые поднимут проект на уровень «сопровождаемый тестовый фреймворк», — это ослабление зависимости тестов от порядка и состояния, введение DTO/Jackson и вынесение дублирующегося авторизационного/тестового кода в общий клиент-слой. Рекомендую начать именно с них.
